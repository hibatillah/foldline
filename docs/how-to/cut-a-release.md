# Cut a release

> **How-to.** Read when: you publish a version, regenerate the license list, or explain how users update. Skip if: you only build locally; see [build, run and debug](build-run-and-debug.md).

Two GitHub Actions workflows exist. `release.yml` does the release. `ci.yml` only checks pull requests into `master`
(see [work with branches](work-with-branches.md)); nothing runs on a push to `master`, so run the checks yourself before
you tag a commit that did not come through a pull request.

| Workflow | Starts when | Does |
| --- | --- | --- |
| `ci.yml` | a pull request into `master` | `cargo fmt --all --check`, `cargo clippy --workspace -D warnings`, `cargo test --workspace`; the **Check** job is what a pull request must pass to merge |
| `release.yml` | a push of a tag that starts with `v` | `cargo fmt --all --check`, `cargo clippy --workspace -D warnings`, `cargo test --workspace`, then builds and publishes a GitHub release (a pre-release when the tag has a suffix, such as `v0.5.0-alpha.1`; see [share a pre-release](#share-a-pre-release)) |

It installs the MSVC toolchain, because the settings crate (GPUI) does not build with the GNU one. Locally use `cargo +stable-x86_64-pc-windows-msvc` for the settings crate.

`scripts/perf.sh` is not in the workflow: it moves the mouse and needs a real, unlocked desktop. Run it yourself before a release.

## Release notes

The release notes are written for you when the tag is pushed (`scripts/release-notes.sh`, called by `release.yml`):

- They list the pull requests merged since the previous release, grouped by `type:` label as `.github/release.yml` says
  (Breaking changes, Features, Fixes, Performance and refactors, Other changes; chore, docs, test, style, ci and build
  are left out). Each line is the pull request's title, credited to its **assignee**, or to its author when nobody is
  assigned, with a link to the pull request.
- The `type:` label comes from the pull request's title: the CI workflow sets it from the `type(scope):` prefix.
- A stable tag covers everything since the last stable tag, so `v0.5.0` collects the changes of its pre-releases; a
  pre-release covers what came after the tag before it (`scripts/previous-tag.sh`).
- Changes pushed straight to `master` are not pull requests, so a release made only of them lists commit titles instead.
- To see the notes before you push: `bash scripts/release-notes.sh v0.5.0 master` (it reads what is on `origin`).

Assign each pull request to the person who should be credited when you open it.

## Publish a release

1. Set `version` under `[workspace.package]` in `Cargo.toml` (for example `0.2.0`; every crate inherits it) and commit it to the default branch.
2. Run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` (MSVC toolchain); the workflow runs them again and a failure there leaves a tag to delete.
3. Tag the commit and push the tag:

   ```
   git tag v0.2.0
   git push origin v0.2.0
   ```

The release workflow stops at once if the tag does not match the workspace version in `Cargo.toml`, so a tag can never publish a
build under the wrong number. It then produces a release named after the tag with:

- `<name>-v0.2.0-windows-x64-setup.exe`: the installer, built from `installer/notch.iss` with Inno Setup. It installs
  the notch and the settings program (`notch-settings.exe`, which the tray menu starts from the notch's folder) for the
  current user (no administrator rights), with the project license, the license of the font built into the notch
  (`Geist-LICENSE.txt`) and `THIRD-PARTY-LICENSES.txt` beside them, adds a Start menu entry and, unless unticked, starts the notch with Windows
- `<name>-v0.2.0-windows-x64-setup.exe.sha256`: its SHA-256 checksum
- release notes generated by GitHub from the commits since the previous tag

`<name>` is the package name in `crates/notch/Cargo.toml`, so renaming the crate renames the installer with no workflow change.

## Third-party licenses

`THIRD-PARTY-LICENSES.txt` holds the license texts copied from the sources of every crate linked into the two
executables (the settings program links Apache-2.0 GPUI crates, which require their license text to ship). It is
committed and generated: run `scripts/third_party_licenses.sh` after any `Cargo.lock` change and commit the result. The
script reads `cargo metadata` for the MSVC target, follows normal dependencies only, and groups crates by identical
text. Crates whose sources contain no license file are listed at the end of the file with their declared license.

## Updating

A user updates by downloading the newer `-setup.exe` and running it. The installer finds the copy that is already
installed (by its fixed `AppId` in `installer/notch.iss`), says which versions are involved and asks whether to
continue, then closes the running notch, replaces it in place and starts it again. Nothing in the notch checks for new
versions or uses the network for it. Never change the `AppId`, or the installer stops recognising earlier installs.

## Notes

- The orange folded-tab icon comes from `assets/branding/logo.png`. Regenerate `logo.ico` with
  `scripts/export-icon.sh` after changing it. Cargo embeds it in the executable; Inno Setup uses the same export for
  the setup executable and the master PNG for the wizard header. The Start menu shortcut and installed-app entry use
  the icon embedded in `notch.exe`.
- The installer is not code-signed, so Windows SmartScreen may warn people who download it. Free signing for open
  source projects exists (SignPath Foundation); it needs an application from the project owner, and signing is then one
  more step in `release.yml`.
- The installer is built only by the release workflow. To build it by hand, install Inno Setup and run
  `ISCC /DAppVersion=0.2.0 /DExeName=notch.exe /DSourceExe=<release notch.exe> /DSettingsExeName=notch-settings.exe /DSourceSettingsExe=<release notch-settings.exe> installer
otch.iss`; the result
  goes to `installer\Output` unless `/O` says otherwise (the workflow uses `dist`).
- The workflow installs the latest stable Rust (MSVC host), so a new Rust release can add a Clippy warning that fails the release. Fix the
  warning; do not pin an old compiler unless a release is urgent.
- To delete a bad release, delete the release and its tag on GitHub (or `git push --delete origin <tag>`), fix, and tag
  again.

## Share a pre-release

For a build a teammate should try before the real release, tag it with a SemVer suffix:

1. Set `version` under `[workspace.package]` in `Cargo.toml` to the coming number (for example `0.5.0`), commit and push.
2. `git tag v0.5.0-alpha.1 && git push origin v0.5.0-alpha.1`

The tag is `v<crate version>-<stage>.<number>`: `alpha` (rough, a few testers), `beta` (feature-complete, still tested),
`rc` (release candidate), then the plain `v0.5.0`. SemVer orders them `alpha < beta < rc < final` and compares the number
as a number, so write `alpha.2`, not `alpha2`. The crate version stays `0.5.0` for the whole series.

`release.yml` checks only the part of the tag before the first `-` against the crate version, builds the same installer
and publishes the release as a pre-release, so it is not shown as the latest one. The installer carries the whole tag
version (`0.5.0-alpha.1`), which the update prompt and Add or remove programs show. The settings window's sidebar shows it
too: the Build step passes it as `NOTCH_RELEASE_VERSION` (the tag without the `v`), and a local build without it shows the latest pre-release tag of the current version series (`crates/settings/build.rs` reads it from `git describe`), or the plain crate version when there is none. Inno Setup cannot compare a suffixed
version, so over an installed copy the prompt reads "Replace it with version 0.5.0-alpha.1?" and the user confirms; a
plain version still gets "Update it to…". Delete the pre-release and its tag when it is no longer needed.

In Claude Code, `/release <version | major | minor | patch | alpha | beta | rc | stable>` does these steps up to the push: it works out the next tag from the latest one (`/release beta` after `v0.5.0-alpha.2` gives `v0.5.0-beta.1`; `/release minor beta` gives the first beta of the next minor), checks that `master` is clean and green, sets the crate versions when the base number changes, commits and tags locally, shows the result and asks before pushing the commit and the tag.

For code that is not committed, run `scripts/test-build.sh`: it builds the working tree into `dist/` (an installer with
Inno Setup installed, otherwise a zip) and needs no GitHub.
